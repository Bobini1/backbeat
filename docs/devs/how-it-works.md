### Bundles

Bundles are _the_ essential piece of backbeat. Everything else is built ontop of it.

They are regular charts, wrapped in some additional information. They are JSON files with a `.bb` extension, and look like this:

The `chart` field is a base64-encoded, `gzipped` chart file. It's not encrypted or anything, it's just compressed and binary-safe.

We combine a chart with an `assets` lookup table. That lookup table says this:

> When this chart asks for `0x1311.png`, it is referring to a file whose contents have the sha256 checksum `63073fba1bfe7a041bde5e851ba930fd95367136cd9137b32a6e761fc6e2992c`.

That _one_ trick is what underpins the whole design of Backbeat.

The `filename` field is provided so that things integrating with the store know how to _interpret_ the chart itself; a game can say "I only want charts with the `.sm` extension", et cetera.

The `desc` field is a human readable description of the chart. This is generated by the packager, when packaging the chart; it's nice for debugging, and it's nice to show people things that aren't just "Unknown Chart".

Backbeat doesn't actually know anything about your chart formats - it supports all existing formats and all future formats, because it doesn't care at all what the chart file or format is. That's why the `desc` is needed, otherwise, backbeat would have to know how to parse the sm file to describe it!

One more very important thing:

> **A bundle is for exactly ONE chart**. No more, no less.
> In some games, like stepmania, multiple charts are mixed into one chart file.
> This is **NOT CORRECT** for backbeat.
>
> Your packager **MUST** break the charts into their individual units.
> Think of it this way - when a table says `chart sha256/abc... has a level of 10`, and you've packaged `abc...` in a way where there's two charts in there, that's definitely wrong. Backbeat becomes unusable if you violate this.

### Bundle ID

There's a `bundleId` algorithm. The details are in the spec, but the short of it is that it's a unique, deterministic identifier for `(filename, assets, chart_bytes)`.

In plain english, it identifies "this chart, with these assets".

### Combined Assets ID

There is a second algorithm - `combinedAssetsId`, which identifies "these assets" on its own.

Essentially, just a stable ID of the `assets` field. More details in the spec if you care.

## Assets

An asset is just a file referred to by a song. It can be a song, background image, text file, anything. Files are identified by their `sha256` checksum.

## The Store

The backbeat store is a specification for storing files on disk. You can think of it as a special `Songs/` folder that you use via the backbeat library rather than the filesystem.

Users can control where their store is in their config file, but they can only have one store. Combining it with the above two things, you get something like this:

```
.assets/
  63/07/3fba1bfe7a041bde5e851ba930fd95367136cd9137b32a6e761fc6e2992c
  c2/01/579dd1b1489727fe97295a02fc06e3722d8fedf52ba6ceb8b4197b5cda54
  ...
backbeat.db
```

Since things are identified by their checksums, you natively deduplicate assets. When a chart refers to `file.wav`, you look up what the bundle says that should map to, and then return that.

This is how we get deduplicated storage, and fast re-use of existing assets.

At a high level, the store provides functions like:

- checking whether a chart, bundle, asset, or collection is installed;
- retrieving chart, bundle, and asset data by ID;
- listing and inspecting installed packs, tables, and courses;
- adding and removing data servers;
- downloading charts, bundles, and assets from configured servers;
- tracking and cancelling downloads;
- importing and exporting content; and
- attaching the store's SQLite database for read-only queries.

## Servers

Backbeat servers are HTTP, static file servers. They have the following endpoints:

- `GET /backbeat/up`
  Returns an empty file, used to check whether you're online or not.

- `GET /backbeat/info`
  Who runs this server?

- `GET /assets/<asset-sha256>`
  If this server has it, return a file with this ID.

- `GET /bundles/<bundle-id>`
  If this server has it, return a bundle with this ID.

- `GET /charts/<id-algorithm>/<id-value>`
  If this server knows about it, return a bundle that has this chart ID.

This is a novel endpoint - you can do e.g. `/charts/md5/2b00042f7481c7b056c4b410d28f33cf` and, if they have it, you can get it!

- `GET /precombined-assets/<combined-assets-id>`
  This is a niche endpoint for optimising downloads - for charts that have _lots_ of assets (BMS has 1000+ at times), doing 1000 individual downloads can add a minute of latency to downloads. This is an optimisation where servers can precombine assets.

The stock server doesn't ship with this code, so clients can _try_ this and then fall back to regular downloads (don't worry, they're still fast!)

## Collections

It's cool to get charts on your system, but having a big soup of unorganised charts isn't interesting to anyone. Just ask USC players.

Backbeat supports three kinds of "collections", which are ways of organising charts.

Collections are identified by URLs. You just add a `https://example.com/asdf` to your client. Anyone can host a collection anywhere, and they're not tied to content servers.

### Packs

Packs are groups of bundles. They're the same deal as Stepmania Packs, and are functionally like "albums".

All fields here are mandatory.

They look like this:

## How it all connects

Combining all these pieces, you can probably figure out the rest of it. When you ask for the chart, all you have to do is request `<server>/charts/...` or `<server>/bundles/<bundle-id>` and cascadingly download assets.
